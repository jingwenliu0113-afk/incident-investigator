# M1 smoke test — Mac（2026-10-08，兩輪）

- 目的：Core §1 收尾。確認鎖定的 OTel Demo 3.1.0 stack 在 Mac arm64 上真的能跑、實際跑的是 lock 裡的 image、telemetry 有流到 backend，
  並記錄環境本身的不穩定因素。**這不是正式 incident collection**：沒有保存 snapshot，也沒有 ground truth。
- 機器：`mac`（Apple M4 Pro，48 GB）；Docker Desktop 4.93.0（Engine 29.8.1），VM linux/aarch64、12 CPU、16 GB，containerd image store。
- 環境：`env/otel-demo.lock.json`（upstream `dedc017`），以 `uv run python -m env compose up` 啟動（自動帶入鎖定的 up 參數）。
- 原始證據（gitignored）：`data/external/smoke/2026-10-08-m1/`（run 1）、`data/external/smoke/2026-10-08-m1-run2/`（run 2）。

| | Run 1：互動式檢查 | Run 2：不介入的觀察 |
|---|---|---|
| 時間（UTC） | up 08:06:05 → 收集證據約 08:17 → down 約 08:18 | up 08:34:59 → 觀察 08:35:25–08:50:30 → down 08:50:32 |
| Heavy lock | 07:37:27–約 08:18（含 pull）；以等待 release 檔的 process 持有，最後由 wrapper 釋放 | 整段 up → 觀察 → down → verify 包在同一個 `with-mac-lock` process |
| 做了什麼 | pull、啟動、各種查詢（Jaeger / Prometheus / OpenSearch / Locust）、flagd 生效時間測試 | 每約 12 秒取樣 product-catalog 的 docker stats / health；每約 36 秒讀它的 memory cgroup；每約 72 秒讀 Locust stats；觀察期間**不做任何互動查詢** |

## 問題（依證據歸因；都是鎖定環境本身的性質）

### 1. product-catalog 長期貼著 20 MiB memory cgroup 上限運作（最重要）

- 證據：
  - Run 2 讀 cgroup（25 個樣本）：`memory.current` 全程 **17.1–19.9 MiB / 20 MiB**（anon 約 7.9–9.3 MiB、file 約 6.4–10.4 MiB、swapcached 約 4.5–8.2 MiB）。
  - `memory.events max`（碰到上限而觸發回收的次數）在 15 分鐘內從 116 增加到 **86,416**，越到後面增加得越快。
  - `docker stats` 會扣掉 inactive file cache，所以 run 1 量到的 5.5–16.5 MiB **低估了**實際壓力。
- Run 1 的後果：
  - 08:08:49 被 cgroup **OOM-kill** 一次（Docker VM kernel log：`Memory cgroup out of memory: Killed process … (product-catalog)`，`constraint=CONSTRAINT_MEMCG`），由 `unless-stopped` 拉回。
  - 約 08:15:4x 起**再次卡住**，到收集證據時（約 08:17:14）都還沒恢復，結束時間沒有觀察到：
    - 收集證據當下 `FailingStreak=10`（Docker 只保留最後 5 次 probe，所以連續失敗大約從 08:15:4x 開始；Locust 第一個 504 在 08:15:55）。
      保留下來的 5 次（08:16:23 起）依序是 `failed to connect service ":3550"` → `health rpc did not complete` → 三次 `Health check exceeded timeout (5s)`。
      因為 Retries=20，Docker 仍然顯示 healthy。這個盲點已修：`verify-running` 現在會回報連續失敗的 probe。
    - product-catalog 在 08:16:31–08:16:56 有 4 次 OTLP export timeout。
    - Locust 收集當下的 p50 / p95 都是 15 s（Envoy timeout）。
- Run 2 的 15 分鐘內沒有 OOM、沒有重啟、沒有 504；每約 12 秒的取樣都沒有看到連續失敗的 probe，結束時最後 5 次 probe 全部通過（無法排除取樣之間的單次失敗）。
  product-catalog CPU p50 5.5%、p90 16%，08:47:17 有一個 229% 的尖峰，剛好落在回收次數增加最快的 08:46:53–08:47:29 區間。
- 推論（未完全證實）：OOM-kill 確定是 memcg 上限造成的；08:16 的卡住**推測**也跟它一直在記憶體回收與 swap 的邊緣運作有關，但沒有直接證據，觸發條件也還沒有釐清。
  會讓 request 或記憶體增加的 fault（lock contention、catalog failure、大量 traffic）很可能讓它更頻繁地發生。
- 處理：不修改鎖定環境。調高上限會偏離 upstream，必須先寫 decision log（列在 `NEXT.md`，第一次正式收集前要決定）。

### 2. Run 1 冷啟動時有 504 風暴

- 08:06:50 起，frontend → product-catalog 的 `GetProduct` / `ListProducts` 要 26–52 s，超過 Envoy 的 15 s timeout。
- 在 Jaeger 查到的範圍內，product-catalog server span（含 astronomy-db 查詢）p50 在 08:06–08:07 約 3 s、最高約 19 s；08:09 那一分鐘最高 26 ms。
  後來 08:16 又卡住一次（見問題 1）。
- 同時期 product-catalog 有 2 次 OTLP export timeout（08:06:55、08:08:04）；collector 自己的 log **沒有** timeout。
- Run 2（image 已在本機、沒有互動查詢）**沒有**出現這種情況。
- → Run 1 是剛 pull 完 11.7 GB 後的第一次啟動，又同時在做互動查詢；目前不能把它歸因於單一原因。
  正式收集需要暖機期與「穩定」的判斷條件，**只排除前幾分鐘不夠**，見問題 1。

### 3. OpenSearch exporter 因 mapping 衝突丟棄 log

- 錯誤：`mapper_parsing_exception: Could not dynamically add mapping for field [http.request.method]. Existing mapping for [attributes.http] must be of type object but found [text]`。
- 某些 log 的 `attributes.http` 是字串，其他 log 帶巢狀的 `http.*` 欄位，帶到後者的文件就被 OpenSearch 拒收（permanent error，不會重試）。
- Run 1 的 collector log（08:06:37–08:17:14）：**308 個 export request 失敗**，exporter 記錄的 `dropped_items` 共 4,822 筆，其中逐筆的 mapping 拒收共 **1,624** 次。
  OpenSearch bulk API 是逐筆處理的，所以實際遺失量應該介於 1,624 與 4,822 之間（未驗證）。08:10 左右在 OpenSearch 查到約 1,000 筆。
- Run 2 同樣持續發生：430 個 request 失敗、`dropped_items` 8,176、mapping 拒收 3,073 次。
- → OpenSearch 不能當 snapshot 的 source of truth。這是 M2 raw export 設計時的輸入；依指示，M2 的設計決策留到進 M2 時再寫 decision log。

### 4. `ask_agent` 持續失敗（研究預測已證實）

- load-generator 的 `POST http://agent:8010/prompt` 會出現 `gaierror(-2, 'Name or service not known')` / `NameResolutionError`，因為我們的 compose 組合沒有 agent stack。
- 數量：
  - Run 1：全程 523 個 request 中 24 次。
  - Run 2：959 個 request 中 79 次，約 5.4 次/分（約 14.5 分鐘）、8.2%；每個約 72 秒的取樣區間增加 3–11 次。這是 run 2 **Locust 錯誤中**唯一持續出現的（OpenSearch 的 mapping 拒收也持續發生，見問題 3）。
- → 處理方式要在第一次正式收集前決定（decision 003）。

### 5. 其他

- Collector 自己的 log 會回流到 logs pipeline（run 1 的 OpenSearch 中 `otelcol-contrib` 有 411 筆）。
- Prometheus exporter 在 run 1 暖機期失敗 1 次。
- Upstream compose 把 network 名稱寫死成 `opentelemetry-demo`（不帶 project 前綴）。
- Load-generator 沒有 stdout log（`--skip-log-setup`）。
- Run 2 啟動瞬間有 2 次 DNS 失敗（frontend-proxy 還沒就緒）。

## Smoke test 期間做過的變更與診斷資源

- 為了測 flagd 生效時間，`adFailure` 開啟約 1 秒，之後以原始 bytes 還原（smoke test 不收集資料）。
- 讀 Docker VM 的 dmesg 時，暫時用了 `alpine:3`（`--rm --privileged --pid=host`）；結束後刪除了這個 image。
- 為了確認 container inspect 的格式，曾用鎖定的 Prometheus image `docker create` 一個 `ii-inspect-probe`。
  當時 `docker rm` 沒有加 `-v`，留下一個 anonymous volume（`ed5c71e9…`，08:02:52Z 建立；內容是該 image 的空 `/prometheus`）。
  確認來源後已用名稱刪除。MACHINE_POLICY 已補上「診斷 container 用 `--rm` 或 `rm -v`」。
- Run 2 讀 cgroup 時用鎖定的 Prometheus image 跑 `docker run --rm --network none --cgroupns=host`（唯讀，沒有新增 image）。
- 沒有動到任何不屬於本 Project 的 Docker 資源：`pgvector/pgvector:pg17`、`rtu-maintenance-platform-db-1`、它的 volume `rtu-maintenance-platform_rtu_db_data` 與 network `rtu-maintenance-platform_default` 都保持原狀。
