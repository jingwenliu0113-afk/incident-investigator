## 1. 版本與 image（→ decision 001）

- Tag `3.1.0` 是指向 `dedc017` 的 lightweight tag，也就是 `898ede2`（Prepare release，#3968）的 parent。
  所以 tag 上 `IMAGE_VERSION=3.0.0`，第三方 image 也還是舊版（collector 0.159.0、jaeger 2.19.0、grafana 13.1.0、postgres 18.4、prometheus v3.13.1、valkey 9.0.4、flagd v0.16.0）。
- 每個 demo service 都是 `image: ${IMAGE_NAME}:${DEMO_VERSION}-<svc>`，搭配 `DEMO_VERSION=latest`。
  `latest-*` 等於 `nightly-*`（每天 00:00 UTC 從 main 重新 build），而 compose 預設 pull policy 是 missing，
  所以實際跑哪個 image 取決於本機快取。同時有 `image:` 和 `build:`，pull 失敗時還會改用本機原始碼 build。
- 全部 21 個 `3.1.0-<svc>` image（以及 agent / mcp / chatbot / frontend-tests）的 SLSA provenance 都是 `vcs.revision=dedc017`，
  而且都有 linux/arm64 與 linux/amd64；Docker Hub `otel/demo:3.1.0-*` 的 digest 與 ghcr 相同。
- arm64 image 是在 x64 runner 上用 QEMU cross-build 的；upstream CI 的 telemetry tests 只跑 amd64。
- `IMAGE_VERSION` 會進入 `OTEL_RESOURCE_ATTRIBUTES`（`service.version`）與 currency 的 `VERSION` env。
  upstream `.env` 在解析時就把 `OTEL_RESOURCE_ATTRIBUTES` 展開了，所以後面的 env file 只覆寫 `IMAGE_VERSION` 不會影響它（已在本機實測確認）。

## 3. Fault 控制機制

- flagd v0.16.0 用 `--uri file:` 在 compose 下每 1s 用 `os.Stat` 輪詢，只有 **mtime 比之前新**才會重新載入。
  - `rename()` 會保留來源檔的 mtime，所以事先準備好的舊檔 `mv` 過去可能被忽略：要寫一個新的 temp 檔再 rename。
  - 如果輪詢時剛好讀不到檔案（不是原子替換），flagd 可能就此**不再監看**這個檔案，直到重啟。
- flagd-ui：`GET /feature/api/read`、`POST /feature/api/write`（body `{"data": <完整 flagd JSON>}`，需要 `Content-Type: application/json`）。
  寫入是非同步的（先回 `{}` 再寫），而且**不驗證內容**，只要是合法 JSON 就會直接寫進去。flagd-ui 只在開機時讀一次檔案。
  經過 Envoy `:8080` 呼叫的話，會在 snapshot 裡留下 frontend-proxy 的 span / access log；flagd-ui 自己的 Phoenix span 也會標出注入的時間點。
- 同樣的 flag 狀態可能有不同的 bytes（API 寫入是 compact，UI 寫入是 pretty-print），寫入時還會出現 `demo.flagd.json.tmp`
  → injection record 用 canonical JSON hash（`collect.records.canonical_json_sha256`）。
- flagd-ui scheduler（#2375）：開機時是 `running: false`；只能從 `/feature/scheduler` 頁面啟動，沒有任何 env / REST / config 可以控制。
  容器關閉時「還原被它開啟的 flag」是 race condition，不保證會發生。

## 4. Telemetry 路徑（→ M2 raw export）

- Core 的 collector 只輸出到 `debug` exporter（basic verbosity），什麼都不會留下。只有加上 `compose.observability.yaml`，
  才會有 traces→Jaeger 2.19（in-memory，最多 25,000 筆）、metrics→Prometheus（OTLP，保留 7d，**`VOLUME /prometheus` 會跨 run 保留**）、logs→OpenSearch。
- Collector config 依序載入：base → full → observability → extras。map 會深度合併、list 會被**整個取代**。
  要匯出 raw 資料，最穩的做法是在 extras 裡加**新的 pipeline**（例如 `traces/snapshot`）並使用 `file` exporter（contrib 0.159.0 內建，alpha）。
  `file` exporter 預設 `append: false`，collector 重啟時會清空檔案，所以要用 rotation、append 或每個 run 用不同路徑。
  （更正，decision 008：「每個 run 用不同路徑」擋不住同一個 run 內的重啟或 SIGHUP 清空；採用 `append: true`。）
- upstream 的 traces pipeline 在任何 exporter 之前，就會先改寫 span 名稱（`set_semconv_span_name`，留下 `original_span_name`）、
  遮蔽 / 刪除敏感 attribute（`redaction.*.count`）、加上 resource detection → **要決定 snapshot 收的是處理前還是處理後的資料**。
- observability 模式會丟掉 `prometheus/ad` receiver；collector 的 debug / 自身 log 會回流進它自己的 logs pipeline。
  （更正，decision 008：實際拿掉 `prometheus/ad` 的是 full layer 的 metrics receivers list；observability 一定會載入 full，所以在我們的組合裡效果相同。）
- 沒有 filelog receiver（container stdout 不會被收集）。flagd-ui、image-provider、telemetry-docs 沒有 OTLP logs。
- Metric 解析度：SDK metrics 與 span_metrics 每 60s；docker_stats / postgresql 每 10s。fault 持續時間若太短，每個 series 只有很少的點。
- 預設 28 個 container，compose memory limit 合計約 7.7 GiB。
- Jaeger 2.21（不在我們的 pin 裡）移除了 legacy query API → snapshot 工具要對 2.19 寫、對 2.19 測。
  （更正，decision 008：2.21 只移除 UI 已經不用的 v1 HTTP endpoints；而且 snapshot 不從 Jaeger 匯出，改由 collector 的 raw pipeline 取得。）

## 5. Traffic generator（→ decision 003）

- Locust 2.44.4、Python 3.14.7、locust-plugins 5.0.3（Playwright）。task 權重（總和 32）：index 1、browse_product 10、get_recommendations 3、get_ads 3、
  view_cart 3、add_to_cart 2、checkout 1、checkout_multi 1、flood_home 5、ask_agent 3。

- 只寫在 `.env` 的變數**不會**進入 container，除非 compose 的 `environment:` 有列出來（例如 `LOCUST_SPAWN_RATE`、`LOCUST_RUN_TIME`、seed）。
- 所有 load 都被標成 synthetic：`synthetic_request` baggage、`user_agent.synthetic.type=test`、`demo.payment.charged=false`。
- ~~Browser span 可能根本到不了 collector~~ → **smoke test 推翻**：`frontend-web` 的 trace 有進 Jaeger（見 §7 runtime 結果第 4 點）。
- Locust web API 沒有驗證、綁在 0.0.0.0 的隨機 host port。

## 7. 要在 smoke test 確認的 runtime 問題

1. 全部 container 在 M4 arm64 上 healthy（特別是 JVM：ad / fraud-detection / kafka / opensearch，以及 Playwright Chromium）。
2. 實際的 RepoDigests 等於 lock。
3. `ask_agent` 是否持續失敗、量有多大。
4. 5 個 user、權重 9:1 是否真的會產生 1 個 browser user；browser span 是否有送到 collector。
5. 從 host 原子寫入 flag 檔後，flagd 是否在約 1s 內套用（Docker Desktop 的檔案分享 + mtime）。
6. Collector 在 macOS 的 `/hostfs`、docker.sock mount 是否正常（hostmetrics 量到的是 Docker VM，不是 macOS）。
7. Grafana 13.1.0 是否還支援 runtime 的 `GF_INSTALL_PLUGINS`。

### §7 的 runtime 結果（2026-10-08 Mac smoke test）

1. 全部 running，JVM 沒有 SIGILL，Chromium 正常（`frontend-web` 有 trace）。**product-catalog 不穩定**：暖機期被 cgroup OOM-kill 一次（20 MiB 上限），約 08:15:4x 起又卡住，直到收集證據時都還沒恢復（健康檢查連續失敗 10 次，被 Retries=20 遮蔽而仍顯示 healthy）。
2. RepoDigests / platform manifest 等於 lock（`python -m env verify-running`）。
3. `ask_agent` 持續失敗：run 1 的 523 個 request 中 24 次；run 2 的 959 個 request 中 79 次（約 5.4 次/分）。
4. Browser user 至少 1 個；**browser span 有送到 collector**（§5 的推測不成立）。
5. flagd 在 host 原子寫入後 0.33–1.04 s 套用。
6. Collector 的 hostmetrics / docker_stats 正常（量到的是 Docker VM）。
7. Grafana 13.1.0 仍支援 `GF_INSTALL_PLUGINS`（會印 deprecated 警告），裝上的是 opensearch-datasource v2.34.4。

新發現：OpenSearch exporter 因 `attributes.http` mapping 衝突拒收 log：run 1 的 collector log 中有 308 個 export request 失敗（`dropped_items` 4,822），逐筆拒收 1,624 次；run 2 是 430 / 8,176 / 3,073。
新發現：product-catalog 長期貼著 20 MiB memory cgroup 上限運作（`memory.events max` 15 分鐘內 86,416 次），推論是它間歇性卡住與 OOM 的機制（尚未完全證實）。
詳見 `docs/smoke-tests/2026-10-08-m1-mac-smoke.md`。
